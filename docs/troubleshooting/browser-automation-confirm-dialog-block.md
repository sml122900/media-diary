# 다면 별점 축 삭제 확인창(`window.confirm`)이 크롬 브라우저 자동화(CDP)를 블록

## 문제 상황

Phase 13.3 `AxisRatingPicker`의 축 삭제(🗑) 버튼을 브라우저 자동화로 클릭해 UI를
검증하던 중, `window.confirm()`이 뜬 순간부터 이후 모든 자동화 명령이 응답 없이
멈췄다. Chrome DevTools Protocol(CDP) 기반 도구로 클릭·스크린샷·페이지 이동을
시도했지만 전부 30초 타임아웃과 함께 "The renderer may be frozen or
unresponsive"를 반환했다.

이 프로젝트는 2026-08-05에 이미 같은 근본 증상을 겪은 적이 있다 — 안드로이드
실기기 WebView에서 `Runtime.evaluate`가 응답 없이 멈췄고, 원인 중 하나가 JS
`confirm()` 다이얼로그의 렌더러 블로킹이었다(CLAUDE.md 트러블슈팅 로그 2026-08-05
"CDP(`Runtime.evaluate`)가 응답 없이 멈춤" 항목 참고). 이번엔 실기기가 아니라
**데스크톱 크롬 자동화**에서 같은 클래스의 문제가 재발했다는 점을 확인해야
했다 — 원인이 동일한지, 우회 방법이 이번에도 있는지가 관건이었다.

## 시도한 것들

### 1. 클릭 재시도

축 삭제 버튼을 다시 클릭 → `Input.dispatchMouseEvent`가 동일하게 타임아웃. 다이얼로그가
이미 화면을 점유한 상태라 이후 입력 이벤트가 페이지에 전혀 도달하지 않음을 시사했다.

### 2. 스크린샷으로 현재 상태만 확인

`Page.captureScreenshot` → 역시 30초 타임아웃. 페인트 캡처조차 렌더러 메인 스레드가
살아 있어야 가능한데, 다이얼로그 대기 중엔 그것도 불가능하다는 걸 확인했다.

### 3. 새 URL로 navigate 시도 (다이얼로그 우회 기대)

"페이지 이동은 브라우저 레벨 명령이라 페이지 JS 블로킹과 무관하게 동작하지
않을까"라는 가설로 시도 → `Page.navigate`도 응답 없이 멈춤. 이 자동화 도구가
CDP의 `Page.handleJavaScriptDialog`를 노출하지 않는 이상, 브라우저 레벨 명령조차
우회 경로가 없다는 것을 확인했다.

### 4. 같은 액션 반복 대신 세이프티 가이드라인 확인

여기서 같은 실패 액션을 계속 재시도하는 대신(가이드라인상 2~3회 실패 후엔
루프를 멈추고 사용자에게 확인해야 함), 사용자에게 브라우저 창에서 직접
확인창을 닫아달라고 요청하는 쪽으로 전환했다.

## 최종 해결법

CDP 레벨에서는 이미 뜬 네이티브 다이얼로그를 프로그래밍적으로 닫을 방법이
없었다(핸들러 미노출). 사용자에게 브라우저에서 직접 확인/취소를 눌러달라고
요청해 해제했다 — 다이얼로그가 닫힌 뒤에는 탭 그룹 자체가 무효화돼
(`tabs_context_mcp`가 빈 그룹을 반환) 새 탭을 만들어 재로그인 후 검증을 이어갔다.

재발 방지책으로는 다이얼로그 자체를 피하는 게 아니라 **검증 전략을 바꿨다**:
`window.confirm()`처럼 파괴적 동작을 확인하는 흐름은 브라우저 자동화 대신 API
레벨(curl)로 검증하기로 했다. 실제로 이 축 삭제(CASCADE 포함) 로직은 이미
Phase 13.3 커밋 1에서 curl로 전부 검증이 끝나 있었기 때문에, UI 삭제 버튼의
재검증을 스킵해도 커버리지 손실이 없었다 — API로 이미 증명된 로직을 굳이 UI에서
다시 확인하는 것은 다이얼로그 블로킹 리스크만 지는 중복 검증이었다.

## 이력서 소재 한 줄

> 브라우저 자동화(CDP) 검증 중 네이티브 `confirm()` 다이얼로그가 렌더러 전체를
> 블록시키는 현상을 실기기 WebView 사례와 대조해 재확인하고, CDP로는 우회 불가능한
> 제약임을 시도 3가지로 확인한 뒤 무리한 재시도 대신 검증 전략(파괴적 확인 흐름은
> API로, 비파괴적 흐름만 브라우저로) 자체를 바꿔 문서화했다.
