# 2026-08-12 — Phase 13.2: 수식어 공유 카드 (이미지 생성)

## 배경

"인생영화 뭐야?"에 이미지 한 장으로 답하는 기능. Phase 13.1의 수식어 데이터를
1080×1920 PNG로 렌더링해 저장/공유한다. html2canvas 등 신규 렌더링 의존성은 쓰지 않고
Canvas API를 직접 사용.

## 커밋 0 — 사전 조사

1. **CSV 내보내기 파일 저장 방식**: 순수 웹 메커니즘(`Blob` → `URL.createObjectURL` →
   `<a download>`). `@capacitor/filesystem`·`@capacitor/share` 둘 다 미설치, 실기기
   저장 검증 이력도 없음(미검증) — 이 한계를 그대로 승계해 이미지 blob도 동일 패턴 재사용.
2. **포스터 이미지 출처**: 앱 UI가 실제로 채우는 `poster_url`은 전부
   `https://image.tmdb.org/t/p/w300` 하나뿐. 매칭 실패한 수동 입력은 빈 문자열이지
   타 출처 URL이 아님 — taint 리스크 있는 실제 출처 없음.
3. **카드 타이틀용 표시명**: `users.name`(가입 시 필수) 존재, `useAuthStore().user.name`으로
   바로 접근 가능 — 백엔드 변경 불필요.

## 커밋 1 — 카드 렌더러 (`be1480e`)

`frontend/src/utils/epithetCard.js` 신설. 1080×1920 캔버스에 다크 팔레트(`index.css`
`[data-theme="dark"]` 값 그대로 재사용) 배경, 상단 타이틀, 3~6개 부문 행(포스터+이모지+
라벨+대표작 제목·연도+N회 관람 배지), 하단 워터마크를 그린다.

- 포스터는 `crossOrigin="anonymous"`로 로드 후 2×2 오프스크린 캔버스에 그려
  `getImageData`로 taint 여부를 개별 확인 — 한 장이 실패해도 `Promise.all`이 나머지를
  막지 않고, 실패한 행만 제목 텍스트 타일로 폴백.
- 한글/영문 공용 말줄임(`truncateToWidth`)·줄바꿈(`wrapLines`)은 문자 단위 이진탐색으로
  구현(단어 단위가 아니라 CJK에 안전).
- 행 높이·포스터 크기·폰트 크기는 부문 개수(3~6)에 비례해 스케일.

## 커밋 2 — 선택 UX + 저장/공유 (`75f4816`)

`EpithetsPage.jsx`에 "카드 만들기" 진입 → 그리드 카드가 체크 가능한 선택 모드로 전환
(대표작 없는 부문은 비활성) → 하단 바에 "n/6 선택됨" + 3~6개일 때만 활성화되는 "카드 생성" →
미리보기 모달(`.backdrop`/`.add-modal` 재사용) → 저장(Blob+`<a download>`) / 공유
(`navigator.canShare`가 true일 때만 버튼 노출 — 신규 플러그인 없이 점진적 향상).

### 실사용 검증 중 발견한 버그 — TMDB 포스터가 항상 폴백 타일로 떨어짐

브라우저로 실제 3개/6개 카드를 생성해보니 포스터가 하나도 안 뜨고 전부 텍스트 타일로
나왔다. 스펙의 전제("TMDB는 crossOrigin=anonymous로 canvas 사용 가능")를 의심하고
직접 검증:

```
curl -sI "https://image.tmdb.org/t/p/w300/....jpg" -H "Origin: http://localhost:5173"
→ Access-Control-Allow-Origin: *
```

서버는 CORS를 정상 지원한다. 그런데 브라우저에서 `new Image(); img.crossOrigin =
'anonymous'`로 같은 URL을 요청하면 `onerror`가 뜬다. 원인은 캐시였다 — 같은 포스터가
`EpithetCard`/`EpithetDetail` 등 앱 다른 곳에서 이미 crossOrigin 없이 `<img>`로 먼저
로드된 뒤였고, 브라우저가 그 캐시(오염된 상태로 표시된 리소스)를 crossOrigin 요청에도
재사용해버려 서버 재검증 없이 실패했다. 캐시 무효 상태에서 crossOrigin으로 먼저 요청하면
성공하는 것으로 재현 확인.

실사용에서는 사용자가 카드를 만들기 전에 거의 항상 그리드에서 포스터를 먼저 봤을 것이므로
사실상 매번 재현되는 문제였다. 포스터 로더에 캐시 키를 분리하는 더미 쿼리 파라미터
(`?_cors=1`)를 붙여 우회 — 이후 3개/6개 선택 모두 실제 포스터가 정상 렌더링되는 것을
스크린샷으로 확인.

## 검증

로컬 백엔드를 실 Supabase DB에 연결한 상태로 테스트 계정 생성 → TMDB 포스터 3종
(기생충/인터스텔라/위플래시/센과 치히로) + 매칭 실패 수동 입력(포스터 없음, 장문 제목) +
깨진 URL 항목까지 섞어 부문 6개 구성 → 3개 선택 카드, 6개 선택 카드 각각 실제 렌더링
확인(포스터 정상 표시, 폴백 타일 2건 모두 줄바꿈·말줄임 정상) → 저장 버튼 동작(콘솔
에러 없음) → 라이트 모드에서 선택 UI(체크박스·하단 바·미리보기 모달) 확인 → 테스트
계정 삭제로 정리.

실기기 저장/공유·OLED 화질 검증은 사용자 몫으로 남김(스펙 명시 사항).

# Phase 13.3: 다면 별점 (커스텀 평가 축)

## 배경

단일 별점("내 별점", `user_media.rating`)의 한계 해소 — "작품성은 5점, 나에겐 3점"처럼
여러 기준으로 평가. 수식어(13.1)와 동일 철학: 기본 제공 프리셋은 씨앗일 뿐, 생성·수정·삭제
전부 유저 소유. `user_media.rating`은 대표 축으로 스키마·의미·통계/정렬/카드/CSV/공유
카드 전부 무변경 — 이번 기능을 모르는 화면은 하나도 안 깨짐(설계 전제이자 검증 항목).

## 커밋 1 — 스키마 + CRUD (`f703cfc`)

`user_rating_axes`(축: label/emoji/sort_order) + `user_media_axis_ratings`(축별 점수:
user_media_id, axis_id, rating — `user_media.rating`과 동일하게 CHECK 없는 INTEGER)
2테이블. `GET/POST/PATCH/DELETE /api/rating-axes` + `PUT/DELETE
/api/user-media/:id/axis-ratings/:axisId`는 수식어(`epithets.js`) 컨벤션 그대로(라벨
1~20자, 중복 409+기존 id, 소유권 미스매치 404).

curl로 로컬 백엔드를 실 Supabase DB에 연결해 검증: 축 생성→부여→점수 수정→해제→축
삭제(CASCADE) 사이클, 교차 유저 404(axis·media 각각 독립 확인), 재시청 2회차 행에
1회차와 다른 축 점수 부여(구조상 자동 성립 — `user_media_id`가 회차마다 다른 행이라
그대로 됨). 전부 통과 후 테스트 계정 삭제로 정리.

## 커밋 2 — DetailModal UI (`5ca74ef`)

`AxisRatingPicker.jsx` 신설(`EpithetPicker.jsx` 패턴 준용) + DetailModal "내 별점" 바로
아래 다면 별점 섹션. 결정 사항 3가지(기술 결정 로그 참고):

1. **축 점수 조회**: 신규 GET(`/api/rating-axes`)이 축+`items[]`를 함께 반환 — 수식어의
   `GET /api/epithets` 구조를 그대로 복제. media별 상세조회에 얹는 대신 이 방식을 택한
   이유는 축 자체가 유저 전역 리소스라 어차피 별도 목록 조회가 필요했기 때문.
2. **해제 UX**: 이미 매긴 별을 다시 탭 → 0점 → DELETE. 재시청 별점 입력에 이미 있던
   `r === n ? 0 : n` 토글을 그대로 재사용, `StarRating` 컴포넌트 자체는 무수정.
3. **관리 UX**: 전용 페이지 신설 없이 피커 안에서 이름 변경(✎)/삭제(🗑) 인라인 처리.
   재정렬 드래그 UI는 저비용 우선으로 이번엔 생략(`sort_order` 컬럼·API만 존재).

브라우저로 실 DB 대상 전체 사이클 검증: 계정 생성 → 영화 추가 → 피커에서 프리셋
탭(축 생성) → 별 4개 부여(피커·본문 양쪽에서 동시 반영 확인) → 본문에서 같은 별
재탭(해제, DetailModal에 행이 사라짐) → 피커 재오픈 → ✎로 이름 변경(라벨 재사용 가능
확인) → 라이트 모드 전환 후 동일 화면 재확인. 테스트 중 축 삭제 확인창(`window.confirm`)이
브라우저 자동화 렌더러를 블록시켜 수동 개입 필요했음(트러블슈팅 참고) — 삭제 자체의
CASCADE 동작은 커밋 1에서 curl로 이미 검증됐으므로 UI 재검증은 스킵. 테스트 계정은
API로 정리.

## 트러블슈팅 — `window.confirm`이 브라우저 자동화를 블록

축 삭제 버튼 클릭 시 뜬 `window.confirm()`이 CDP(`Input.dispatchMouseEvent`,
`Page.captureScreenshot`, `Page.navigate` 전부)를 30초 타임아웃으로 멈춤 — 이 프로젝트
CLAUDE.md에 이미 기록된 "JS `confirm()`이 렌더러를 블록"(2026-08-05, 실기기 WebView
사례)과 동일 현상이 데스크톱 크롬 자동화에서도 재현. CDP로는 다이얼로그를 못 닫아
사용자에게 수동으로 확인창을 닫아달라고 요청 — 닫힌 뒤에도 tabId가 무효화돼 새 탭에서
재로그인 후 이어감. 재발 방지: 삭제 확인이 필요한 흐름을 자동화로 검증할 땐 API(curl)로
대체하고 브라우저는 non-destructive 조작까지만 다룰 것.
