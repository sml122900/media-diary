# 기술 결정 — 공백 1개 삽입 검색 fallback (선형 변형)

## Problem (상황/문제)

> TMDB Search API가 한글 쿼리를 공백 기준으로 토큰 매칭한다. "다크나이트"(붙여쓰기)로 검색하면
> "다크 나이트", "다크 나이트 라이즈"가 결과에서 누락되고, "파이트클럽"도 "파이트 클럽"을 찾지 못한다.
> 우리가 제어할 수 없는 외부 API의 토큰화 방식이라 완전한 해결은 불가능하고, 현실적인 fallback이 필요했다.

## Action (결정 및 근거)

> 최초 제안은 "무차별 대입은 조합 폭발(combinatorial explosion)이라 위험하다"는 판단으로
> UX 안내 문구(띄어쓰기를 다르게 시도해보라는 힌트)만 추가하는 소극적 방향이었다.
>
> 이 판단은 틀렸다는 피드백을 받았다: **공백을 정확히 1개만 삽입하는 경우 변형 개수는
> `글자수 - 1`개로 선형(linear)이지, 지수(exponential)가 아니다.**
> - "파이트클럽"(5글자) → 4개 변형 (그중 "파이트 클럽" 포함)
> - "다크나이트"(5글자) → 4개 변형 (그중 "다크 나이트" 포함)
>
> 공백 2개 이상을 조합하면 실제로 폭발하지만, 1개 삽입만으로 실사용 대부분의 케이스(단어 2개 결합)를 커버할 수 있다.
>
> 이에 따라 `frontend/src/api/tmdb.js`에 다음 조건의 fallback을 구현했다:
> - **트리거 조건**: 1차 검색 결과가 3개 미만 AND 입력에 공백 없음 AND 한글 2~12자 (`/^[가-힣]{2,12}$/`)
> - **변형 생성**: 각 위치에 공백 1개씩 삽입한 `(길이-1)`개 쿼리
> - **호출 상한**: 최대 12개 변형까지만 병렬 조회 (긴 쿼리에서 API 콜 폭증 방지)
> - **병합**: 1차 결과 + fallback 결과를 `tmdb_id` 기준 dedupe 후 popularity 순 정렬
> - **안내 문구**: fallback까지 실패했을 때만 "띄어쓰기를 다르게 시도해보세요" 표시

## Result (결과)

> "파이트클럽" → 파이트 클럽(1999), "다크나이트" → 다크 나이트(2008)·다크 나이트 라이즈가 정상적으로
> 검색 결과에 나타난다. "인터스텔라"처럼 원래 공백이 필요 없는 정답 쿼리는 1차 검색만으로 충분해 fallback이
> 트리거되지 않고, 영어 쿼리는 애초에 한글 정규식 조건에 걸리지 않아 영향받지 않는다.
>
> 반대로 로컬 데이터(내 목록 검색)는 우리가 완전히 제어 가능하므로 fallback 없이
> 검색어·제목 양쪽에서 공백을 제거한 뒤 비교하는 정규화만으로 확실하게 해결했다.

**교훈**: 알고리즘 복잡도를 어림짐작으로 "조합 폭발"이라 단정하기 전에, 실제 변형 생성 규칙(고정 개수 삽입 vs 임의 개수 조합)을 명확히 정의하고 계산해야 한다.
