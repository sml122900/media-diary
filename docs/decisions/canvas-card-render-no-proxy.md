# 기술 결정 — 수식어 공유 카드는 Canvas 직접 렌더링 + 클라이언트 캐시 우회 (프록시 재사용 안 함)

## Problem (상황/문제)

> Phase 13.2는 수식어 3~6개를 1080×1920 PNG 한 장으로 렌더링해 저장/공유하는 기능이다.
> 포스터는 TMDB 원본 이미지를 그대로 캔버스에 그려야 하는데, 이 프로젝트는 정확히 같은
> 유형의 문제를 이미 한 번 겪은 적이 있다 — 2026-05-14 연말 결산(Year in Review) PNG 저장
> 기능에서 html2canvas가 CORS 캐시 오염으로 포스터를 X박스로 그렸고, 그때는 백엔드에
> `/api/proxy/poster` 엔드포인트(TMDB 도메인 화이트리스트, SSRF 방어, 1주일 캐시)를 신설해
> 우회했다.
>
> 이번엔 스펙 자체가 두 가지를 배제했다 — html2canvas 등 신규 렌더링 의존성 금지, 신규
> Capacitor 플러그인은 "보고 후 결정"으로 보류. 과거의 해법(백엔드 프록시)을 그대로
> 재사용해도 되는지, 아니면 이번 제약에 맞는 다른 처방이 필요한지가 실제 구현 전 판단
> 지점이었다.

## Action (결정 및 근거)

> **렌더링은 Canvas 2D API 직접 사용, CORS 문제는 프록시가 아니라 클라이언트 캐시 키
> 분리로 해결했다.**
>
> html2canvas를 쓰지 않기로 한 건 스펙이 이미 정한 것이었지만, 이 프로젝트에 이미
> "불필요한 의존성 지양"이라는 결이 있다는 점(Letterboxd CSV를 외부 파서 없이 20줄로
> 직접 구현한 전례)과도 맞아떨어져 그대로 따랐다. 텍스트·이미지 배치, 말줄임/줄바꿈,
> 둥근 사각형 클리핑까지 전부 `CanvasRenderingContext2D` 기본 API로 직접 구현했다
> (`epithetCard.js`).
>
> 포스터 CORS 문제는 실측으로 원인부터 다시 확인했다. curl로 TMDB 응답 헤더를 직접
> 찍어보니 `Access-Control-Allow-Origin: *`가 이미 있었다 — 즉 2026-05-14 당시와 달리
> **서버는 CORS를 지원한다.** 실패 원인은 같은 포스터 URL이 앱 다른 화면(카드 그리드 등)
> 에서 이미 `crossOrigin` 없이 `<img>`로 로드된 뒤라, 브라우저가 그 캐시를 crossOrigin
> 요청에도 재사용해버리는 것이었다(자세한 재현 과정은
> [`docs/troubleshooting/tmdb-poster-cors-cache-poisoning.md`](../troubleshooting/tmdb-poster-cors-cache-poisoning.md)).
>
> 백엔드 프록시를 다시 쓰는 방법도 있었지만 채택하지 않았다. 카드 한 장에 포스터가 최대
> 6장이라 프록시를 거치면 클라이언트 → 우리 백엔드 → TMDB 왕복이 최대 6회 늘어나는데,
> 정작 원인은 서버 쪽 CORS 미지원이 아니라 **브라우저 쪽 캐시 키 충돌**이었으므로 서버를
> 경유할 이유가 없었다. 대신 `crossOrigin="anonymous"`로 로드할 때만 URL에 더미 쿼리
> 파라미터(`?_cors=1`)를 붙여 캐시 키를 분리했다 — 앱의 다른 화면이 쓰는 캐시 엔트리와
> 겹치지 않게 하는 것만으로 충분했다.
>
> 포스터 로드 실패(taint 포함)는 행 단위로 격리해 텍스트 타일로 폴백하도록 했다 —
> `Promise.all`로 병렬 로드하되 개별 실패가 `catch`로 흡수되어 카드 전체 렌더링을
> 막지 않는다.

## Result (결과)

> 브라우저 실사용 검증에서 TMDB 포스터 3~4종(기생충·인터스텔라·위플래시·센과 치히로)이
> 정상 렌더링됐고, 매칭 실패 수동 입력(포스터 없음)과 깨진 URL 항목은 텍스트 타일로
> 자연스럽게 대체됐다. 신규 백엔드 엔드포인트나 npm 의존성 없이 프론트 유틸 파일 하나로
> 완결됐다.

**교훈**: 같은 증상이 프로젝트 안에서 재발했다고 해서 과거의 해법을 그대로 재사용하는 게
항상 맞지는 않는다. 이번 기능의 제약(신규 의존성 금지, 왕복 최소화)에 비추면 프록시는
과잉이었고, 실측으로 원인을 다시 확인한 덕분에("서버가 CORS를 지원하지 않는다"는 전제가
사실은 틀렸다) 더 가벼운 처방을 찾을 수 있었다. 과거 문서는 참고할 선례이지 그대로
복붙할 정답이 아니다.
